# 승인 계약 강화 delta

## 범위

- 주문 승인 요청에 **화면 표시값 대조**와 **step-up 재인증**을 요구한다(SPEC:966).
- 표시값이 서버 계산값과 다르면 `409` 로 새 확인 화면을 요구한다.
- 이중 승인이 단일 intent 만 만들도록 보장한다(MVP 완료 기준 6번).
- `SUBMITTING` 전이 전까지 compare-and-set 철회를 허용한다. 성공은 보장하지 않는다.
- 공개 `submit` API 를 만들지 않는다(SPEC:964). 승인이 Order 를 만들고 worker 가 직전
  재검증(B3) 후 제출한다.
- `proposalVersion` 은 `TradeProposal`(E1) 이 없으므로 이 delta 범위 밖이다. 승인 대상의
  버전 대조가 필요한 자리는 열어 두고 E1 에서 연결한다.

## 왜 지금인가

실거래 진행이 확정됐다(Phase 0 Q2). 표시값 대조가 없으면 화면에 보인 수량·최대손실과
다른 주문이 실제로 나갈 수 있다. E6 의 선행 필수다.

## 표시값 대조

- 승인 요청은 `displayedQuantity`, `displayedMaxLoss` 를 **필수**로 받는다.
- 서버가 승인 시점에 다시 계산한 값과 다르면 `409` 를 반환한다. 근사·허용 오차로
  통과시키지 않는다. 통화와 소수 정밀도를 포함해 비교 기준을 명시한다.
- `409` 응답은 클라이언트가 새 확인 화면을 그릴 수 있도록 **서버 계산값을 함께** 준다.
- 값이 누락되면 승인하지 않는다. 기본값으로 채우지 않는다.

## step-up 재인증

**요구사항: step-up 토큰은 사람이 최근에 재인증했음을 실제로 증명해야 한다.**

- 아무 검증 없이 발급되는 토큰은 보안 연극이다. 그런 형태로 구현하지 마라.
- 이 저장소는 OIDC 기반이다. 재인증 신선도는 OIDC 의 인증 시각(`auth_time`) 기준으로
  판정하는 것이 표준 경로다. 세션이 인증 시각을 보유하지 않으면 그것부터 확보한다.
- 토큰은 **짧은 수명**이고 **단일 사용**이며 **해당 사용자와 승인 대상에 바인딩**된다.
  다른 주문에 재사용될 수 없다.
- 만료·재사용·타 사용자 토큰은 `401`.
- 원문 토큰을 로그·메트릭 label·감사 레코드에 남기지 않는다(SPEC:1151).

**설계 결정이 필요하면 임의로 절충하지 말고 보고한다.** 증명력 없는 토큰을 넣고
"완료" 라고 하지 않는다.

## 처리 불변식

- 승인은 즉시 제출 의사다. **grace period 를 두지 않는다**(SPEC:966).
- 같은 승인 요청이 재전송돼도 intent 는 하나만 만들어진다. 기존 `Idempotency-Key` 헤더
  경로를 재사용하고 새 멱등 메커니즘을 발명하지 않는다.
- 철회는 `SUBMITTING` 전이 **전에만** compare-and-set 으로 허용한다. 경합에서 지면
  실패를 반환하고, 이후에는 브로커 취소 절차를 쓴다.
- 표시값 불일치·토큰 실패 시 intent 상태를 변경하지 않는다. 부작용 없이 거절한다.
- B3 의 제출 직전 재검증을 우회하는 경로를 만들지 않는다.

## TDD와 검증

- 표시값 불일치(수량) → `409` + 서버 계산값 반환 + intent 상태 불변
- 표시값 불일치(최대손실) → `409`
- 표시값 누락 → 승인 거절, 기본값 대체 없음
- 만료 토큰 → `401`
- 재사용 토큰 → `401`
- 타 사용자 토큰 → `401`
- 다른 주문에 바인딩된 토큰 → `401`
- 이중 승인 → **단일 intent** (MVP 완료 기준 6번)
- `SUBMITTING` 전 철회 성공, 전이 후 철회 실패
- 승인 성공 경로가 B3 재검증을 그대로 거침
- 토큰 원문이 로그·감사에 남지 않음
- backend `./mvnw clean verify`
