# 브로커 주문 전송 포트 delta

## 범위

- `BrokerAdapter` 포트에 주문 전송 계약을 추가한다. 현재 포트는 읽기 5개 메서드뿐이라
  실거래 어댑터를 끼울 자리가 없다.
- `PaperTradingBroker` 를 포트 구현으로 전환한다. 지금은 포트를 구현하지 않는 별도
  `@Service` 로 떠 있다.
- 두 구현이 같은 계약을 만족하는지 검증하는 `BrokerContractTest` 를 추가한다.
- `TossInvestBrokerAdapter` 는 포트를 구현하되 주문 전송은 아직 지원하지 않는 상태를
  **명시적 타입으로 표현**한다. 실제 HTTP 구현은 E6 범위다.
- 기존 읽기 5개 메서드의 시그니처와 의미는 바꾸지 않는다.

## 왜 지금인가

실거래 진행이 확정됐다(Phase 0 Q2). 주문 전송 경로가 포트에 없으면 실거래 어댑터를
붙일 자리 자체가 없고, Paper 와 실거래가 같은 계약을 만족하는지 검증할 수단도 없다.
E6 의 선행 필수다.

## 포트 계약

SPEC:555-559 의 토스 주문 API 형태를 내부 계약으로 정규화한다.

| 메서드 | 계약 |
|---|---|
| `placeOrder` | LIMIT/MARKET. 멱등 키를 필수 인자로 받는다 |
| `cancelOrder` | 브로커 주문 ID 기준 |
| `modifyOrder` | **미국 주식은 가격 변경만 지원한다.** 수량 정정 요청은 계약 위반으로 거부 |
| `getOrder` | 브로커 주문 ID 로 단건 조회 |
| `getOrders` | `OPEN` / `CLOSED` 그룹으로 조회 |

- 반환은 기존 읽기 메서드와 같이 `BrokerResponse` 로 감싼다. 성공·실패·미확정을 타입으로
  구분하고 예외로 흘리지 않는다.
- 전송 결과가 확인되지 않는 상태(`UNKNOWN`)를 표현할 수 있어야 한다. 미확정을 실패로
  뭉개면 E5 의 조정 절차가 성립하지 않는다(SPEC:1055).
- 계좌 범위 외부 주문 ID 중복은 `broker_orders` 의 `UNIQUE(broker_account_id, broker_order_id)`
  가 막는다(SPEC:525). 포트는 이 제약과 모순되는 계약을 두지 않는다.

## 처리 불변식

- 같은 멱등 키로 `placeOrder` 를 재호출해도 브로커 주문이 중복 생성되지 않는다.
- `modifyOrder` 의 수량 변경 시도는 **어느 구현에서도** 거부된다. 정책이 어댑터마다
  다르면 안 된다.
- `getOrders` 의 `OPEN`/`CLOSED` 분류 기준은 두 구현이 같다.
- Paper 구현은 기존 페이퍼 체결 동작을 그대로 유지한다. 포트로 옮기는 것이지 의미를
  바꾸는 것이 아니다.
- Toss 구현의 주문 전송은 **지원하지 않음을 타입으로 반환**하고 조용히 성공하지 않는다.
  E6 에서 실제 전송으로 교체될 때까지 이 상태가 테스트로 고정된다.

## TDD와 검증

- `BrokerContractTest` 가 Paper 와 Toss 양쪽에 **같은 계약**을 검증
- 같은 멱등 키 재호출 시 브로커 주문 미중복
- 수량 정정 시도가 두 구현 모두에서 거부
- `OPEN`/`CLOSED` 분류가 두 구현에서 동일
- 전송 미확정 상태가 실패와 구분되어 표현됨
- Toss 주문 전송이 미지원 타입을 반환하고 조용히 성공하지 않음
- 기존 Paper 주문 워크플로 테스트가 전부 통과 (동작 보존)
- ArchUnit 동결 목록이 늘지 않음
