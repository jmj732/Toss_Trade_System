# kill switch 원장화 delta

## 범위

- 전역·사용자·계좌 단위 kill switch 를 DB 원장으로 만든다(SPEC:962, SPEC:1136).
- `POST /api/v1/trading/kill-switch` 로 조작한다.
- **제출 worker 가 매번 확인한다**(SPEC:1136). B3 가 만든 제출 직전 재검증 관문
  (`PreSubmitRevalidationCheck`)에 SPEC:886 의 10번 항목으로 꽂는다.
- 변경은 감사 기록을 남기고 재인증을 요구한다(SPEC:1159).
- 실거래 진행이 확정됐다(Phase 0 Q2). 폭주를 멈출 수단이 없으면 실거래를 켤 수 없다.
  E6 의 선행 필수다.

## 원장

- `risk_policy_history`(V15)의 버전 이력 패턴을 따른다. 상태를 덮어쓰지 않고 **추가만** 한다.
- 범위 3종: `GLOBAL`, `USER`, `ACCOUNT`.
- **하나라도 켜져 있으면 차단이다.** 범위 간 우선순위로 서로를 무효화하지 않는다.
  좁은 범위가 넓은 범위를 해제할 수 없다.
- 각 변경 레코드에 행위자, 시각, 사유, 범위, 대상 ID 를 남긴다.

## 조작 비대칭 (중요)

- **켜는 것(engage)은 마찰이 없어야 한다.** 비상 정지다. step-up 을 요구하지 않는다.
- **끄는 것(disengage)은 신중해야 한다.** E2 의 step-up 재인증을 요구한다(SPEC:1159).
- 이 비대칭은 의도된 것이다. 반대로 만들면 비상시 정지가 늦어지고 해제가 쉬워진다.

## 처리 불변식

- 제출 worker 는 **매 제출마다** 확인한다. 승인 시점 판정을 재사용하지 않는다.
- 상태를 읽을 수 없으면 **차단한다. fail-closed.** 조회 실패를 통과로 처리하지 않는다.
- 캐시를 두려면 수명을 명시하고, 그 수명이 곧 정지 지연임을 문서화한다. 확신이 없으면
  캐시를 두지 않는다.
- **켜진 상태에서 신규 제출은 전부 차단된다.**
- **이미 제출된 주문은 영향받지 않는다.** kill switch 는 신규 전송을 막는 것이지 기존
  브로커 주문을 취소하지 않는다. 취소가 필요하면 브로커 취소 절차를 별도로 쓴다.
- 차단은 B3 의 관문과 같은 방식으로 처리한다 — 브로커를 호출하지 않고 구체적 사유를 남긴다.
- 단일 사용자 운영이지만(Phase 0 Q2) 범위 3종을 모두 만든다. 비용이 낮고 계좌 단위 정지가
  실거래에서 실제로 필요하다.

## TDD와 검증

- 전역 kill switch on → 신규 제출 전부 차단, 브로커 호출 0회
- 사용자 단위 on → 해당 사용자만 차단
- 계좌 단위 on → 해당 계좌만 차단
- 좁은 범위가 넓은 범위를 해제하지 못함
- **이미 제출된 주문은 영향 없음**
- 상태 조회 실패 → 차단(fail-closed)
- engage 는 step-up 없이 가능
- disengage 는 step-up 필요, 없으면 401
- 모든 변경에 행위자·사유·시각 감사 레코드
- 원장이 덮어쓰기가 아니라 추가만 됨
- backend `./mvnw clean verify`
