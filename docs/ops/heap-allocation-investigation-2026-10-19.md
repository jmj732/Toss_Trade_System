# Staging heap allocation investigation — 2026-10-19

**The original heap allocation cause is still unproven.** The evidence confirms how the incident stalled HTTP and demonstrates a possible SEC allocation path with synthetic inputs; it does not show that this path caused the production OOM.

## Confirmed incident and current snapshot

Runtime diagnostic run `39255015258` counted four `Java heap space` OOM entries in a bounded 36-hour scan of the then-current backend container (up to 10,000 log lines); one returned log row also contained a Tomcat Acceptor termination. This is not a complete historical log guarantee. The incident snapshots showed an 8080 listener with receive queue 101, no Acceptor thread, and failed HTTP/health probes. DB reads and account-sync attempts continued. This supports the failure chain from heap OOM to Acceptor loss and a stalled HTTP path, not the first allocation that exhausted the heap. The earlier operational timeline is in [backend-cd.md](backend-cd.md#read-only-runtime-diagnostic).

Diagnostic run `39261465199` succeeded at `2026-10-19T13:35:43.953Z` on SHA `9c93916`; the current backend had started at `13:13:15.548Z`. It reported SEC enabled, and current JVM heap gauges of 53,502,592 bytes used, 125,915,136 committed, and 389,283,840 maximum. These are current-process values, not measurements from the original OOM process. The low-usage snapshot about 22 minutes after restart does not establish cache warm-up, historical peak usage, or the cause of the old OOM. The SEC `fieldsConfigured=false` and `endpointsConfigured=false` values describe non-empty keys in `SPRING_APPLICATION_JSON` only. They do not mean the effective SEC defaults are missing: [`application.yml`](../../trading-backend/src/main/resources/application.yml#L23) documents SEC's built-in provider mapping and environment-based enablement.

The diagnostic found Docker's `json-file` logging driver and no previous backend container in the current Compose project. The original container's local logs therefore are not available through this run; external log retention was not checked. The run reported heap-dump, JFR, and GC-logging options as unconfigured. Those flags and the diagnostic's allowlisted log counts do not establish whether older forensic files exist or recover the original stack. See the collector fields in [`runtime-readonly-diagnostic.sh`](../../scripts/runtime-readonly-diagnostic.sh#L324) and its sanitized output schema at lines 1417–1440.

## Candidate SEC allocation path

The SEC transport receives an HTTP response as a complete `String` ([`ProviderHttpTransport.java`](../../trading-backend/src/main/java/com/jmj/trade/marketdata/ProviderHttpTransport.java#L84)). `issuerData` parses SEC submissions and company-facts responses into `JsonNode`s and retains them in a six-hour issuer cache ([`SecCompanyFactsProvider.java`](../../trading-backend/src/main/java/com/jmj/trade/marketdata/SecCompanyFactsProvider.java#L335)). When inline fallback data is needed, the provider can consider up to six filing periods (lines 37, 372, and 447–458). Each non-empty merge deep-copies the full company-facts tree (line 387). The inline cache stores parsed `InlineFetchResult` facts, not the merged tree (lines 486–494), so merged copies are temporary while the original issuer tree remains cached.

A bounded probe using the SEC production class with synthetic six-tree input totaling 23,721,366 JSON bytes reported `OutOfMemoryError` and probe exit code 3 at `-Xmx192m`; at `-Xmx384m` it completed all six merges. The failure point varied between probe executions, so no issuer index is attributed. Its approximate 179,348,272–180,832,792 byte baseline (~179–181 MB decimal) represents the process run and cannot be attributed entirely to cached SEC data. The reproducibility harness and results are retained locally at `/private/tmp/investment-heap-audit-probe/` and are not part of this repository. This demonstrates that repeated tree copies can create substantial allocation pressure in this synthetic case. It does not establish production payload size, prove that SEC was active at the historical OOM time, or attribute that OOM to this path.

## Recovery policy and limits

The current image uses `-XX:+ExitOnOutOfMemoryError` and `-XX:MaxRAMPercentage=50.0` ([`Dockerfile`](../../trading-backend/Dockerfile#L13)); Compose retains `restart: unless-stopped` ([`compose.yaml`](../../compose.yaml#L151)). With the staging backend limit of 768 MiB ([`compose.staging.yaml`](../../compose.staging.yaml#L95)), this increases the configured heap budget from the prior roughly 192 MiB estimate to roughly 384 MiB. The new runtime snapshot confirmed the fail-fast and heap-sizing flags are active. This helps replace a JVM after OOM and provides more heap headroom; it does not remove the original allocation pressure or guarantee that OOM will not recur.

**Conclusion:** historical production allocation attribution remains unknown. SEC tree copying is a reproduced candidate mechanism only. The available runtime snapshot is post-restart, and the original container is no longer present in Compose; no production payload measurement or historical allocation stack is available in these artifacts. No application allocation change is made in this investigation.
