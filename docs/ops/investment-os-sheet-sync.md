# Investment OS Sheet sync

The optional `InvestmentOsSheetConfiguration` runs a five-minute Toss sync for one configured connection. That connection is always `ACCOUNT_1`; it is not remapped to the manual account. For the configured user, the canonical portfolio combines the broker-owned `ACCOUNT_1` rows with the manually maintained `ACCOUNT_2` rows from `Investment OS Account State`. `ACCOUNT_2` is read when its single `Account Registry` row has `Sync Mode=MANUAL` and `Enabled=TRUE`. If that registry is missing or unconfirmed, sync records a failed attempt and retains the last accepted combined snapshot rather than dropping `ACCOUNT_2`. Manual rows retain their recorded source, including values such as `USER_SCREENSHOT`.

Toss quotes refresh both accounts' holding rows, while only `ACCOUNT_1` holdings, cost basis, and cash are broker-upserted. A complete quote set allows aggregate and USD metrics to be recalculated; USD total is USD holdings market value plus USD cash from both accounts. KRW cash remains excluded because no verified FX conversion is applied. Unknown cash, incomplete quotes, or mixed currencies do not become zero or get converted. The PostgreSQL lease (`investment-os-sheet-sync`) prevents duplicate workers across instances.

Manual `asOf` is the preferred ACCOUNT_2 date. When that column is absent or blank, a valid `Synced At` value supplies the source timestamp; `Price Synced At` and the sync read time do not. An explicitly malformed date remains unknown. The portfolio reports the oldest complete manual row date and retains each holding's own date and source. A manual date more than seven days old is marked stale. A future date or missing source/date is unverified. Refreshing prices does not advance manual dates. HWM tracking starts from the first verified combined USD total because earlier history is unavailable.

Combined portfolio snapshots are persisted in PostgreSQL and drive the authenticated investment context without reading Google Sheets on GET. Failed or malformed manual reads append a failed attempt and retain the last accepted combined snapshot; they never fall back to an ACCOUNT_1-only portfolio. Structurally valid manual edits can be accepted when quote inputs are partial. Optional order failures affect order reconciliation but do not downgrade an otherwise complete portfolio snapshot. Numeric risk remains visible with stale manual provenance when its quantities, market values, quotes, and USD weights are known, while sizing eligibility requires fresh validated inputs. The Security Snapshot appends combined source/status, account and manual dates, and per-position source coverage without reordering existing columns.

Closed-market freshness uses only the official Toss US market calendar (`GET /api/v1/market-calendar/US`, the same facts as quote freshness). A time is "outside the market" only when no declared interval (`dayMarket`, `preMarket`, `regularMarket`, `afterMarket`) of its New York date or of the next business day contains it. The next business day matters because its day market opens the previous New York evening. Holdings and cash can change in every one of these intervals, including extended sessions. A missing or malformed calendar means the time cannot be verified, so the existing behavior is kept. The sync reuses a fetched calendar for one hour per New York date, so the five-minute loop does not re-request it. The sync makes three closed-market decisions:

- **Account read and post-close capture.** Outside a verified closed gap (or when the calendar cannot verify one), the sync reads the account through `ConnectorService.portfolio`, which is a read-through: it runs a broker account sync on every call. Inside a verified gap, the sync reads only the persisted snapshot (`ConnectorService.persistedPortfolio`, no broker call). If that snapshot was captured in the same gap, it is used as is, so later syncs in the gap make no broker account call. If it predates the gap, or another account sync (dashboard read-through, scheduled refresh) has since failed so the snapshot reports `LATEST_SYNC_FAILED`, the sync runs the existing read-only account sync (`AccountSyncService.syncForMonitoring`: account, positions, buying power; no orders) and re-reads the persisted snapshot. This bounded capture replaces the five-minute read-through retry that used to clear such a failure; `LATEST_SYNC_FAILED` itself is still never accepted, and `SYNC_IN_PROGRESS` does not trigger a capture. A gap allows at most three capture attempts per backend process; after that the previous snapshot stays subject to the existing checks and the sync does not fall back to the read-through. Open/closed orders and quotes are still fetched on every accepted sync, because orders can be placed or cancelled while the market is closed. Without the capture, no account snapshot is taken after the extended session ends: monitoring syncs the account only during the regular session, and the investment-data scheduler syncs it at 08:00 New York, which is inside the pre-market. On weekdays the declared gap between the after-market end and the next day market is about ten minutes, so the capture matters mainly on weekends and declared holidays.
- **Accepting an age-stale snapshot.** A persisted account snapshot that is stale only because of its age (`SNAPSHOT_TOO_OLD`, older than `portfolio.snapshot.max-age`) is still treated as authoritative while the current time is in the same closed gap in which it was captured. No declared interval has started since then, so holdings cannot have traded. Any other stale reason (`LATEST_SYNC_FAILED`, `SYNC_IN_PROGRESS`), partial data, or an unverifiable calendar keeps the snapshot non-authoritative, which records a failed attempt as before.
- **Recording calendar facts.** An accepted snapshot records calendar facts only when its earliest timestamp, the minimum of `account1AsOf` and every row's `Price Synced At`, is outside the market. Those timestamps are compared with the time the payload is recorded, not with the attempt start: the account and quotes are read after the attempt starts, so they are normally a few seconds later than `attemptedAt`. A timestamp later than the recording time is never used. The facts are `sessionReason=PORTFOLIO_CAPTURED_OUTSIDE_DECLARED_INTERVALS`, `sessionReferenceAt` (that earliest timestamp), and `nextDeclaredIntervalStartsAt`. The investment context then keeps those timestamps current until the next declared interval starts. It applies the 15-minute window again from that point, and whenever the facts are absent. Account-sync alerts (`monitoring.portfolio.max-age`) and `PortfolioReadService` staleness for order paths are unchanged.

Production evidence (Saturday 2026-10-10, read-only diagnostic): the accepted snapshot of the 10:47:59 UTC attempt had `account1AsOf` 10:48:04, five seconds after the attempt start, and its three calendar facts were null (as in the 10:42 accepted snapshot). The facts check compared the snapshot timestamps with the attempt start and skipped them, so the 15-minute rule applied all weekend. The read-through also synchronized the broker account on every five-minute sync; the 10:50:17 `PORTFOLIO_NOT_AUTHORITATIVE` failed attempt is consistent with such a sync failing or overlapping another account sync (any stale reason other than `SNAPSHOT_TOO_OLD` is rejected; the exact reason was not in the diagnostic), and a failed latest attempt marks the context `STALE`. When facts are not recorded, the sync logs `closed_market_facts=not_recorded` with the reason, and logs `market_calendar_date` with the failure reason when the official calendar is unavailable. The real Toss calendar payload for a non-business day has not been recorded in this repository; if the Saturday entry does not declare `regularMarket` (key absent rather than `null`), the gap is unverifiable and the existing behavior is kept, which those logs would show.

An incompatible legacy header in `Thesis State` or `Decision Ledger` preserves that tab and its existing archive without copying or rewriting either one. The research mirror still updates compatible tabs, including `Security Snapshot`. If the primary account sync succeeds, these optional tab conflicts return `PARTIAL` with `RESEARCH_MIRROR_SCHEMA_CONFLICT_<tab names>` and mark the existing Reconciliation Log row unresolved; the accepted PostgreSQL portfolio snapshot keeps its original status. Other primary sync failures remain `FAILED`.

The research mirror adds `ThemeId` and `TrendStage` to `Security Snapshot`, and `EntrySetup`, `InitialRiskPrice`, and `OverlayEffect` to `Decision Ledger`. It also projects the risk mark into `Security Snapshot` (`Risk Mark Price`, `Risk Mark As Of`, `Risk Mark Source`, `Risk Mark Basis`, `Risk Mark As Of Basis`, `Risk Mark Status`, `Risk Mark Reason`) and current thesis approval provenance into `Thesis State` (`Approval Actor`, `Policy Version`, `Verification Event ID`, `Revision ID`). Ledger overlay values are keyed by decision ID. When the existing ledger keeps the canonical leading columns and has manual extension columns, sync appends the overlay headers and updates only overlay cells; it leaves existing manual columns, formulas, and archive tabs untouched. New canonical ledger entries append into unused rows while leaving manual extension columns blank. Unrecognized or reordered leading headers remain a partial schema conflict. These values are projections of the authenticated `/investment/context` tactical overlay fields; see [the calculation and API guide](tactical-overlay-v1-calculations.md) for input routes and Context response fields. V60 AI policy and verification event ledgers remain PostgreSQL-owned; the mirror adds no tab and does not use Sheet cells as evidence or policy input. `Thesis State` continues to mirror current thesis and approval-provenance fields, not the append-only verification history or evidence payloads.

Enable only after the target spreadsheet is shared with the service-account email as Editor and the Sheets API is enabled:

```text
INVESTMENT_OS_SHEET_ENABLED=true
INVESTMENT_OS_SHEET_USER_ID=<MINVESTOS user UUID>
INVESTMENT_OS_SHEET_CONNECTION_ID=<Toss broker connection UUID>
INVESTMENT_OS_SHEET_ACCOUNT_LABEL=ACCOUNT_1
GOOGLE_SHEETS_SPREADSHEET_ID=<spreadsheet ID; Doppler only>
GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON=<service-account JSON; Doppler only>
```

`GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON` is never committed or logged. Production reads these values from Doppler `trade/stg`; Compose keeps the feature disabled by default. Manual sync uses the session-authenticated endpoint:

```text
POST /api/v1/investment-os/sheet-sync
```

Connector API keys do not authenticate this endpoint. A Toss portfolio failure leaves published broker and manual rows intact and records a failed combined-snapshot attempt; a Google read failure also preserves the last accepted combined snapshot. Optional order failures do not invalidate otherwise complete portfolio inputs. Incomplete quotes preserve prior prices and do not create a fresh aggregate valuation. No fill price is inferred from an order limit price.
